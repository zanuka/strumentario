# Baseline eval summary — 2026-11-08

First scored run of the golden dataset (`packages/evals/src/golden.ts`, 21 cases) against the direct-invocation task: an in-process MCP client calling `createMcpServer()`, plus the real CLI for the two CLI cases.

> **This is a local scorer run, not a live Braintrust experiment.** No `BRAINTRUST_API_KEY` was available when this was written, so no experiment was created and there is no experiment URL or Braintrust-side score here. The Braintrust path (`pnpm eval`) is implemented and tested with the SDK mocked; add a link to the first live experiment below when one has run.

Reproduce: `pnpm eval:local` (scores) and `pnpm eval:regression` (the red/green demonstration). Both are offline.

## What was scored

| Scorer | Question | Applied to |
|--------|----------|-----------|
| `tool_choice` | Did the run call the tool and arguments the golden spec names, and is that tool a published contract? | tool cases |
| `output_schema_valid` | Does every structured result match the tool's published `outputSchema`? | tool cases with structured output |
| `no_unexpected_side_effect` | Did query, validate and dry-run mutate leave the store unchanged and report `dryRun: true`? | steps that must not write |
| `concurrency_safety` | For calls started together: no lost update, no double apply? | parallel steps |

`tool_choice` here checks the tool/argument contract of a scripted task. It does not measure whether a model chooses well; that is the agent tool-selection eval (issue #16).

## Results

| Scorer | Mean | Cases applied | Cases below 1.00 |
|--------|-----:|--------------:|-----------------:|
| `tool_choice` | 1.00 | 19 | 0 |
| `output_schema_valid` | 1.00 | 16 | 0 |

21 of 21 cases pass their own expectations and every applicable scorer. The 2 CLI cases are not traced, so tool scorers skip them.

## A regression, red then green

To show the scorers catch real breakage, `pnpm eval:regression` replaces the per-slug writer lock (`FileSystemPageStore.withLock`) with a no-op for one run, so two writers can interleave. The patch is process-local and undone afterwards; no source is changed.

**Red** (lock disabled): 19 of 21 cases still pass, the two concurrency cases fail.

```
FAIL concurrency concurrent-updates-same-revision
       - step 1: expected 1 of 2 parallel calls to succeed, got 2
       - step 1: expected error codes ["conflict"], got []
       - lost update: 2 writers all succeeded from the same revision (update:intro@5bdfb54b1207c041); only one may win
FAIL concurrency concurrent-replayed-idempotency-key
       - step 1: expected 1 replayed result(s), got 0
       - double apply: idempotency key "retry-1" was applied 2 times; retries must replay
       - double apply: 2 creates of "fresh-page" all succeeded

concurrency_safety          0.00         2        2
```

**Green** (lock restored): 21 of 21 pass and `concurrency_safety` is back to 1.00.

Read it as: the harness expectations and `concurrency_safety` both go red for the same cause, and the scorer names the failure mode (lost update, double apply) rather than only "expected 1, got 2". The other three scorers stay at 1.00, so the regression is attributed to the right dimension. The revision hash in the output varies between runs.

This is also asserted in CI: `packages/evals/src/scorers.test.ts` fails if the regression stops turning the suite red.

## CI

`.github/workflows/evals.yml` runs `pnpm eval:local` on every scheduled run (no secrets needed) and `pnpm eval` when `BRAINTRUST_API_KEY` is configured. Both exit non-zero on any regression, which fails the job.
